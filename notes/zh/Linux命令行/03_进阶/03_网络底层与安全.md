# 🛡️ 网络底层与安全实战

> **常见真实场景**：
> "知道三次握手还不够：TIME_WAIT 多了会怎样？如何快速排查网络问题？防火墙怎么配？"

## 1. TCP/IP 协议栈实战

### 1.1 三次握手与四次挥手 (Tcpdump 视角)
别只看图，我们要用 `tcpdump` 亲眼看到。

**抓包命令**：
`sudo tcpdump -i eth0 port 80 -nn -S -tttt` (不做 DNS/端口解析 + 显示绝对序列号 + 打印完整时间)

常用参数速记：
* `-nn`：不做 DNS 反查/端口名解析（抓包时建议默认开，避免误判与卡顿）
* `-S`：显示绝对序列号（对照握手/重传更直观）
* `-tttt`：打印带日期的时间戳（方便跟日志对齐）

**场景复现**：你在另一终端 `curl http://1.2.3.4`

**握手 (Connection Establishment)**:
1.  **SYN**: `Client -> Server` (Flags [S], seq 100) -> 我想连你。
2.  **SYN+ACK**: `Server -> Client` (Flags [S.], seq 200, ack 101) -> 好的，我也想连你。
3.  **ACK**: `Client -> Server` (Flags [.], ack 201) -> 知道了，连接建立。

**挥手 (Connection Termination)**:
1.  **FIN**: `Client -> Server` (Flags [F.], seq 101) -> 我话说完了，挂了。
2.  **ACK**: `Server -> Client` (Flags [.], ack 102) -> 知道了 (此时 Server 还能发数据)。
3.  **FIN**: `Server -> Client` (Flags [F.], seq 201) -> 我也说完了，挂了。
4.  **ACK**: `Client -> Server` (Flags [.], ack 202) -> 好的，再见。

### 1.2 经典面试题：TIME_WAIT vs CLOSE_WAIT

*   **TIME_WAIT**:
    *   **谁产生**：**主动断开连接的一方** (通常是 Client，但在反向代理中 Nginx 是 Client)。
    *   **现象**：`ss -ant state time-wait | head` 看到很多条。
    *   **原因**：主动关闭方发完最后一个 ACK 后，需要等待 2MSL 时间，确保 Server 收到了 ACK。如果 Server 没收到会重发 FIN，Client 需要在 TIME_WAIT 状态下再次发送 ACK。
    *   **危害**：在“需要大量主动外连”的角色上会消耗本地临时端口（比如反向代理连上游、服务端大量短连接访问数据库/Redis/HTTP 上游）。端口耗尽时，新连接会失败。
    *   **优先优化（更安全）**：
        1. 应用层：连接复用/连接池/keepalive，减少短连接（比任何 sysctl 都更优先）。
        2. 端口资源：确认临时端口范围是否过窄：`cat /proc/sys/net/ipv4/ip_local_port_range`。
        3. 观测：看 socket 汇总与状态分布：`ss -s`、`ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn | head`。
    *   **谨慎项**：`tcp_tw_reuse` 很容易被“抄答案”误用。它主要影响主动发起连接一侧的复用行为，并不适合无脑开启；在不同内核版本/网络环境（特别是 NAT/负载均衡路径复杂）下可能带来难以解释的连接异常。把它当作“最后手段”，并在开启前先把连接复用与端口范围做对。
*   **CLOSE_WAIT**:
    *   **谁产生**：**被动关闭的一方** (Server)。
    *   **现象**：Server 收到了 FIN，回了 ACK，但**没有发送自己的 FIN**。
    *   **原因**：**代码 Bug**。程序逻辑卡住了，没有调用 `close()` 关闭 socket。
    *   **结论**：发现大量 CLOSE_WAIT，直接找开发改代码，不是系统配置问题。

一个能迅速定位 “TIME_WAIT 是谁产生的” 的命令：

```bash
ss -ant state time-wait '( sport = :80 or dport = :80 )' | head
```

## 2. Linux 防火墙：从入门到实战

虽然底层是 `iptables`/`nftables`，但日常使用推荐更简单的工具：`ufw`（Ubuntu/Debian）或 `firewalld`（CentOS/RHEL）。

### 2.1 ufw 基础用法（推荐新手）

**安装与启用**：
```bash
sudo apt install ufw
sudo ufw enable
```

**常用操作**：
```bash
# 查看状态与规则
sudo ufw status numbered

# 开放端口
sudo ufw allow 80/tcp        # 允许 HTTP
sudo ufw allow 443/tcp       # 允许 HTTPS
sudo ufw allow 22/tcp        # 允许 SSH

# 封锁 IP
sudo ufw deny from 192.168.1.100

# 删除规则（按编号）
sudo ufw delete 3

# 重置所有规则
sudo ufw reset
```

### 2.2 firewalld 基础用法（CentOS/RHEL）

```bash
# 查看状态
sudo firewall-cmd --state

# 查看已开放服务
sudo firewall-cmd --list-all

# 开放端口（permanent 表示永久生效）
sudo firewall-cmd --permanent --add-port=80/tcp
sudo firewall-cmd --permanent --add-port=443/tcp

# 重新加载配置
sudo firewall-cmd --reload

# 封锁 IP
sudo firewall-cmd --permanent --add-rich-rule='rule family=ipv4 source address=192.168.1.100 reject'
```

### 2.3 iptables 快速了解

虽然有了高级工具，但理解 iptables 对排查问题很有帮助：

**查看规则**：`sudo iptables -L -n --line-numbers`

**封锁 IP**：
```bash
sudo iptables -I INPUT -s 192.168.1.100 -j DROP
```

**注意事项**：
- 很多发行版当前是 nftables 后端（iptables 命令只是前端）
- 遇到"命令能跑但结果看不懂"，优先确认系统实际使用的是 `iptables-legacy` 还是 `iptables-nft`

## 3. 实战排查案例

### 3.1 案例：TIME_WAIT 过多导致连接失败

**症状**：服务器偶尔报错 "Cannot assign requested address"

**排查步骤**：
```bash
# 1. 查看 TIME_WAIT 数量
ss -ant state time-wait | wc -l

# 2. 确认是谁产生的（看本地端口分布）
ss -ant state time-wait | awk '{print $4}' | cut -d: -f2 | sort | uniq -c | sort -rn | head

# 3. 检查临时端口范围
cat /proc/sys/net/ipv4/ip_local_port_range

# 4. 查看 socket 汇总
ss -s
```

**解决方案**（优先级从高到低）：
1. **应用层优化**：使用连接池/keepalive，减少短连接（最有效）
2. **扩大端口范围**：`sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"`
3. **谨慎开启 tw_reuse**：仅用于主动外连场景，不适合所有情况

### 3.2 案例：CLOSE_WAIT 泄露

**症状**：服务运行一段时间后无法响应，`ss` 看到大量 CLOSE_WAIT

**排查步骤**：
```bash
# 1. 查看 CLOSE_WAIT 数量与分布
ss -ant state close-wait | head

# 2. 定位是哪个进程
ss -antp state close-wait | grep <端口>
```

**根本原因**：代码 Bug！程序收到对方 FIN 后没有调用 `close()` 关闭 socket。

**解决方案**：检查代码中的连接关闭逻辑，确保所有连接都在 finally 块中关闭。

### 3.3 案例：防火墙导致服务不可访问

**症状**：服务已启动，但外部无法访问

**排查步骤**：
```bash
# 1. 确认服务在监听
ss -tlnp | grep :80

# 2. 测试本地访问
curl http://localhost:80

# 3. 查看防火墙规则
sudo ufw status numbered    # 或 sudo firewall-cmd --list-all

# 4. 临时关闭防火墙测试（仅测试环境）
sudo ufw disable
```

**常见陷阱**：
- 云服务商的安全组/网络 ACL 也需要配置（防火墙只是其中一层）
- Docker 会自动修改 iptables 规则，可能与 ufw 冲突

### 3.4 案例：DNS 解析慢导致连接超时

**症状**：`curl` 访问外部服务很慢，但 `ping IP` 正常

**排查步骤**：
```bash
# 1. 测试 DNS 解析速度
time nslookup www.example.com

# 2. 查看 DNS 配置
cat /etc/resolv.conf

# 3. 测试直接访问 IP
curl http://93.184.216.34  # example.com 的 IP
```

**解决方案**：
- 更换更快的 DNS 服务器（如 8.8.8.8、1.1.1.1）
- 在 `/etc/hosts` 中添加常用域名映射
- 检查 `/etc/nsswitch.conf` 中的 hosts 配置顺序

## 🎓 专家专题

> **说明**：以下内容面向内核开发者/网络专家，90% 的应用开发者只需了解核心概念即可。

### eBPF：内核级观测与网络编程

**什么是 eBPF**：Linux 内核中的虚拟机，可以安全地注入代码到内核运行。

**核心用途**：
- **高性能网络**：Cilium 等云原生网络方案底层依赖 eBPF
- **系统观测**：BCC 工具集提供零侵入的性能分析
- **安全监控**：Falco 等安全工具使用 eBPF 检测异常行为

**BCC 工具箱示例**：
```bash
# 安装
sudo apt install bpfcc-tools

# execsnoop：监控全系统谁在运行什么命令
sudo execsnoop-bpfcc

# opensnoop：监控谁在打开什么文件
sudo opensnoop-bpfcc

# tcptop：实时 TCP 流量排行
sudo tcptop-bpfcc 1
```

**注意事项**：
- BCC 工具需要 root 权限，且对内核版本有要求（通常 4.9+）
- 不同发行版的包名后缀不同（Debian 系常见 `*-bpfcc`）
- 生产环境使用前需评估性能影响

**替代方案**：
- `bpftrace`：一条命令写脚本，适合临时观测
- `bpftool` / `libbpf-tools`：更偏原生 eBPF 工具链

### iptables 深度配置

**四表五链架构**：
- **表**：filter（过滤）、nat（地址转换）、mangle（包修改）、raw（原始处理）
- **链**：INPUT、OUTPUT、FORWARD、PREROUTING、POSTROUTING

**连接跟踪机制**：
```bash
# 查看连接跟踪表
sudo conntrack -L

# 查看连接跟踪统计
sudo conntrack -S

# 调整最大连接数
sudo sysctl -w net.netfilter.nf_conntrack_max=655360
```

**NAT 配置示例**：
```bash
# 端口转发：将本地 8080 转发到 80
sudo iptables -t nat -A PREROUTING -p tcp --dport 8080 -j REDIRECT --to-port 80

# SNAT：修改源地址
sudo iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -j MASQUERADE
```

### 网络调优参数

**关键 sysctl 参数**：
```bash
# 查看当前值
sysctl net.ipv4.tcp_keepalive_time
sysctl net.core.somaxconn
sysctl net.ipv4.tcp_max_syn_backlog

# 临时调整
sudo sysctl -w net.core.somaxconn=65535

# 永久调整（写入 /etc/sysctl.conf）
echo "net.core.somaxconn=65535" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

**重要参数说明**：
- `net.core.somaxconn`：listen() 的 backlog 上限（默认 128，高并发需调大）
- `net.ipv4.tcp_max_syn_backlog`：半连接队列大小
- `net.ipv4.tcp_keepalive_time`：TCP keepalive 探测间隔
- `net.ipv4.tcp_fin_timeout`：FIN-WAIT-2 状态超时时间

### perf：系统级性能分析

**基础用法**：
```bash
# 安装
sudo apt install linux-tools-common linux-tools-generic

# 记录 10 秒的系统调用
sudo perf record -e syscalls:sys_enter_* -a sleep 10

# 查看报告
sudo perf report

# 实时查看性能事件
sudo perf stat -a sleep 5
```

**网络相关观测**：
```bash
# 观测 TCP 重传
sudo perf record -e skb:skb_clone -a sleep 10

# 观测网络中断
sudo perf record -e irq:irq_handler_entry -a sleep 10
```

### 内核模块与网络协议栈

**查看已加载的网络相关模块**：
```bash
lsmod | grep -E 'bridge|veth|tun|tap'
```

**动态加载/卸载模块**：
```bash
sudo modprobe bridge
sudo rmmod bridge
```

**协议栈调优**：
- RPS/RFS：多队列网卡的中断分发优化
- XDP：eXpress Data Path，在内核最早阶段处理包（高性能场景）
- AF_XDP：用户态直接访问网络包（零拷贝）
